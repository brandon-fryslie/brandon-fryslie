# Stats Card Archive

Historical record of every "Live GitHub Stats" card that has appeared on the profile README. Written by `.github/scripts/sync-stats-archive.py`, which the `stats` job in `.github/workflows/daily-highlights.yml` runs each morning; not hand-edited.

## File layout

```
stats-archive/
  YYYY/
    MM/
      YYYY-MM-DD-HHMMSS.svg    ← the card, copied verbatim out of git history
      YYYY-MM-DD-HHMMSS.json   ← that day's headline numbers, for the gallery
```

- The stamp is the **author** date, in UTC, of the commit that introduced the card. Author date rather than committer date on purpose: the job's push loop rebases when it races the `doodle` and `narrative` jobs, and rebasing rewrites committer dates. Stamping from the committer date would let an already-archived card reappear under a second name after any contended push.
- Year and zero-padded month directories keep any single directory browseable in the GitHub UI and `ls`.
- Multiple entries on the same date are normal — every commit that changed the card gets its own file, so a day with two runs holds two cards.
- The `.json` sidecar is **not** a copy of `assets/daily-stats.json`. It holds only what the gallery renders — the day's metrics, plus the SHA of the commit the card came from. The full data seam already exists in git history at that SHA, and a second copy of it could only ever disagree with the first.

## How entries get added

The archive is **derived from git history**, not accumulated by copying files aside.

Every version of `assets/daily-stats.svg` that has ever been committed is a card that was live on the profile, so the commit log is already the authoritative list of *which* cards existed — of the slots. Each run, the sync script walks that log, fills any slot missing from the tree, and regenerates [`STATS.md`](../STATS.md) from the tree. History decides the slots; the tree owns their contents, which is what leaves room for remastering (below).

Three properties follow from that, and they are the reason for the design:

- **Backfilling and daily operation are the same operation.** There is no `--backfill` flag because there is nothing for one to select. The first run recovered six months of cards; every run since adds one.
- **It self-heals.** A run that was skipped, failed midway, or lost to a force-push is repaired by the next run, because the script compares history to disk rather than tracking what it has already done.
- **The gallery cannot drift from the tree.** `STATS.md` is regenerated by scanning the archive directory, so a card that is not on disk is not in the gallery and there is no third place to check. (The doodle archive works the other way round — the job copies the live SVG aside and *prepends* a gallery entry — which is why its gallery and its tree have to be kept in agreement by hand.)

Because history only contains what has been committed, the card authored on any given morning is archived by the *next* run. The live card is always the one on the README; the archive begins at yesterday.

## Where the captions come from

Each entry's caption carries that day's headline numbers so the gallery can be skimmed without opening 150 SVGs. Two eras produced the cards, and the sync script resolves both to one shape at ingest, so nothing downstream knows the difference:

- **August 2026 onward** — the card is authored fresh each day by a Claude invocation over `assets/daily-stats.json`. That seam is committed alongside the card, so the numbers are read straight from it.
- **Through July 2026** — the card came from the deterministic generator, which rendered every metric as a fixed trio of font sizes (value, label, period). Those are read back out of the card's own text.

The legacy reading is structural, not a guess: the count of values must equal the count of labels, or the card gets **no** caption at all. A caption assembled from mismatched labels and values would state numbers this profile never showed, which is worse than a card with no caption.

## What this archive is not

- **Not a scratch directory.** The only thing that writes a card here is a script — `sync-stats-archive.py` fills empty slots from history, `remaster-stats-card.py` replaces a deterministic card with an authored one. Hand-editing an SVG in this tree is always wrong: the change has no generator behind it, so nothing can reproduce or explain it later.
- **Not the gallery's second opinion.** `STATS.md` is regenerated by scanning this tree, so the two cannot disagree. If they ever look like they do, the page is stale — re-run the sync script; never patch the tree to match the page.

## Remastering

Cards from before August 2026 came from the deterministic generator, and they mostly say a number three times in three font sizes. `.github/scripts/remaster-stats-card.py`, driven by `.github/workflows/remaster-stats-archive.yml`, replaces them one slot at a time: it reconstructs the day's real numbers with `generate-stats-svg.py --as-of <that card's instant>` and hands them to the same stats-card agent, under the same prompt, that authors the card every morning.

Two consequences to know about:

- **A remastered card is not the card that was live** — it is a different picture of the same morning. The *numbers* do reconstruct exactly: run under the Actions token, replaying a past instant reproduces that day's committed values. Two gaps remain and neither is closeable. Repos deleted or made private since then are gone from the query. And where a metric's definition has since been fixed, the remastered card shows the number the day actually earned rather than the one it displayed — the August 1 card said `Days Active 96` because the old generator's count was being truncated by the search API's 1000-result cap; the remaster says `250`. The slot's stamp, date, and originating commit are unchanged, so it still sits exactly where that day's card sat.
- **A card the agent could not author is not archived.** The stats-card prompt tells the agent to copy in the deterministic fallback rather than ship something inaccurate or illegible — the right answer for the daily job, which owes the profile a card that morning. Here it would swap one deterministic card for another while marking the slot done, so `remaster-stats-card.py archive` compares the result against that run's fallback and fails instead. The job goes red, the slot stays pending, and the next dispatch picks it up again.
- **Which slots are still pending is not tracked anywhere.** A sidecar's `source` already answers it: `data-seam` means the numbers came from a machine-readable seam, which is what an authored card is. A remaster writes `data-seam`, so a slot leaves the pending set by *being done* rather than by being recorded as done — the same reason there is no `--backfill` flag next door. Re-running the workflow is always safe and always picks up where the last run stopped.

This is why `sync-stats-archive.py` fills only empty slots and leaves full ones alone. Re-deriving every slot from history each morning would silently undo each remaster overnight — and worse, would re-caption the new card with the numbers the old one rendered, since the sidecar is where the gallery reads its figures.
